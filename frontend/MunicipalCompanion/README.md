# Municipal Elections Companion

SwiftUI iOS client for the COMP4977 Municipal Elections assignment. It consumes
the JWT-protected ASP.NET Core REST API (see `../../src`) and implements:

- **Login / Registration** with client-side validation (required fields, email
  format, password length ≥ 6); the JWT is stored in the **Keychain**.
- **Municipalities** list with logos and election dates, drilling down into
  positions and then candidates.
- **Candidate Directory** with server-side name search plus municipality /
  position filters; each row shows photo, name, **position and municipality**.
- **Candidate Detail** with biography, contact links, and an
  "Add to Voting Guide" action (disabled when already saved).
- **Voting Guide** — the signed-in user's saved candidates, with
  swipe-to-delete and a context-menu remove action.
- **Profile** — user info, logout, and API base URL editing.

Architecture: MVVM (`Models/`, `ViewModels/`, `Views/`, `Services/`, `Support/`)
with `URLSession` + async/await, `NavigationStack`, and
`ObservableObject`/`@Published` (Swift 5 language mode, iOS 16+ APIs only). No
third-party dependencies.

## xtool packaging (verified against xtool 1.22.2)

xtool packages a SwiftPM app from **exactly one library product**, not an
executable target (verified against the `xtool new` template and xtool's
`PackLib` planner: a plain `.library` with `library: ["automatic"]` type is
required). `Package.swift` uses tools-version 5.9 so all targets build in the
Swift 5 language mode.

`xtool.yml` (schema v1) recognizes: `version`, `bundleID` or `orgID`,
`product`, `infoPath`, `entitlementsPath`, `iconPath`, `resources`,
`extensions`, `skipLSP`. There are **no display-name/version keys** — xtool
generates `Info.plist` values itself (`CFBundleShortVersionString` "1.0.0",
`CFBundleIdentifier` from `bundleID`, `CFBundleName`/`CFBundleExecutable` from
the product name, `MinimumOSVersion` from the iOS deployment target) and
**merges our `Info.plist` over the generated one** (custom keys win). Our
plist therefore only overrides `CFBundleDisplayName` ("Municipal Elections
Companion") and the supported orientations — and must NOT contain
`CFBundleIdentifier`, because xtool does not expand build-setting placeholders
and a merged placeholder would clobber the real bundle id.

## Building and running on this machine

The Darwin SDK is already generated and an iPhone is paired, so no SDK
installation or container step is needed. From this directory:

```sh
xtool dev build         # compile for iOS and produce ./xtool/MunicipalCompanion.app
xtool dev run           # build (if needed), install and launch on the device
```

Note: the Swift toolchain is managed by swiftly — if `xtool dev` reports
"Failed to obtain Swift version", source `~/.local/share/swiftly/env.sh`
first (or add it to your bash profile).

`xtool dev run` installs, signs (via the already-configured Apple ID
provisioning), and launches the app on the connected iPhone. When launched
from the CLI it streams device stdout; Ctrl-C detaches without stopping the
app.

## Running on macOS (simulator / Xcode, optional)

```sh
cd frontend/MunicipalCompanion
xtool dev             # builds, boots an iOS simulator, installs and live-syncs
```

or generate an Xcode project for IDE work:

```sh
xtool dev generate-xcode-project
open MunicipalCompanion.xcodeproj
```

Note: do not just `open Package.swift` — the package exposes a *library*
product (the shape xtool requires), so a plain SwiftPM scheme has no runnable
app. Use `xtool dev` or the generated project above.

## API base URL

A `.env` file is shipped inside the app bundle via `xtool.yml` `resources`
(it is tracked in git; the root `.gitignore` ignores `.env` files globally,
so this directory's `.gitignore` re-includes it with `!/.env`). `AppConfig`
reads its `API_BASE_URL` key on every launch and syncs it into UserDefaults
key `apiBaseURL`, so the env value overrides everything — including any
stale stored value. Editing the URL on the **Profile** tab is a per-session
override that remains effective until the next launch, when the bundled
`.env` value is re-applied. Fallback chain: bundled `.env` → UserDefaults →
hardcoded `http://127.0.0.1:5000`.

The shipped `.env` sets
`API_BASE_URL=https://mems-assignment-app.azurewebsites.net` (the Azure App
Service deployment), so both a physical device and the simulator use the
cloud API with no manual configuration.

App Transport Security is **not** relaxed: `Info.plist` has no exception, so
plain `http` endpoints are blocked. If you point the Profile override at a
local `http://` backend for development, either serve it over HTTPS or add a
narrow ATS exception for that host.

Image URLs returned by the API are relative paths (`/uploads/...`);
`mediaURL(from:)` in `Support/Utilities.swift` resolves them against the
configured base URL before `AsyncImage` loads them.

## API contract (implemented by `ApiService`, verified against the live API)

| Method | Path | Auth | Notes |
| ------ | ---- | ---- | ----- |
| POST | `/api/auth/register` | no | `{fullName,email,password}` → `{token,email,fullName}`; 400 problem-details on validation errors |
| POST | `/api/auth/login` | no | `{email,password}` → `{token,email,fullName}`; 401 problem-details on bad credentials |
| GET | `/api/municipalities` | no | array of municipalities; `description`/`logoUrl` nullable |
| GET | `/api/municipalities/{id}` | no | municipality + `positions[]` |
| GET | `/api/positions` | no | array of positions |
| GET | `/api/positions/{id}` | no | position + `candidates[]` |
| GET | `/api/candidates` | no | array of candidates; `biography` is **nullable** (mapped from entity `Profile`) |
| GET | `/api/candidates/{id}` | no | single candidate |
| GET | `/api/candidates/search?name=xxx` | no | filtered candidates |
| GET | `/api/savedcandidates` | yes | array of `{id,candidateId,dateSaved,candidate}` |
| POST | `/api/savedcandidates` | yes | `{candidateId}` → 201 `{id,candidateId,dateSaved}`; 409 duplicate; 404 unknown |
| DELETE | `/api/savedcandidates/{id}` | yes | 204; 404 unknown |

All JSON is camelCase. Dates are plain ISO-8601 with `Z`
(`2026-10-17T00:00:00Z`, `2026-10-15T20:57:04Z`) and are decoded with a
tolerant strategy that also accepts fractional seconds and offset-less
timestamps. Errors are RFC 7807 problem-details
(`{type,title,status,detail,traceId}`; ASP.NET validation bodies add
`"errors": {"Field": ["..."]}`) and are surfaced as readable messages via
`ApiError`.
